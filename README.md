# 1. Приложение

## 1.1. Запуск
Для запуска приложения необходим Python версии 3.12 и выше.

- Запуск через `uv`
    ```console
    uv run python -B ./src/main.py
    ```

- Запуск через `python`
    ```console
    python -B ./src/main.py
    ```

_Примечание: флаг `-B` отключает генерацию .pyc файлов кэша байткода, что позволяет держать файловую структуру чистой, но немного увеличивает время запуска_

## 1.2. Использование
После запуска приложение предложит 3 опции: добавить или удалить предмет, выйти из приложения.

- Опция "добавить предмет" выведет список доступных предметов. Затем предлагается выбрать сам предмет и заполнить его поля. В случае неправильного ввода программа указывает на ошибки.

- Опция "удалить предмет" предложит ввести `uuid` предмета для удаления. Найти его можно в списке предметов в информации о парке.


# 2. Применение SOLID

- **SRP (Single Responsibility Principle)** — был применен принцип единственной ответственности (каждый компонент решает только одну задачу)
  
    - `Auditor` проверяет предметы // ему неважно, как организовано хранение
  
    - `Storage` хранит предметы // ему неважно, как прошел аудит
  
    - `Manager` объединяет методы `Auditor` и `Storage` // ему неважно, как реализован аудит или как хранятся предметы

    - `Item` хранит базовую информацию о предмете // ему неважны другие свойства (аналогично с остальными предметами)

- **OCP (Open-Closed Principle)** — был применен принцип открытости-закрытости (компоненты открыты для расширения, но закрыты для изменения)

    - `SimpleManager` принимает контракты `Auditor` и `Storage`. Если нужно изменить логику аудита или хранения, достаточно поменять передаваемые классы

    - Есть возможность добавления любого нового предмета, и `Manager`, и `Auditor`, и `Storage` будут корректно с ним работать без изменения их самих

- **LSP (Liskov Substitution Principle)** — был применен принцип подстановки Барбары Лисков (наследники не должны существенно менять поведение родительского класса)

    - `Vehicle` наследуется от `Item`, и везде, где ожидается `Item`, передача `Vehicle` даст такой же правильный результат, т.к. логика хранения одинаковая

    - Аналогично, везде где ожидается `Vehicle`, передача `Bicycle`, `Scooter` и т.п. не приведет к ошибочному результату

- **ISP (Interface Segregation Principle)** — был применен принцип сегрегации интерфейсов (не нужно зависеть от неиспользуемого функционала)

    - `EnergyConsumer` выделен в отдельный контракт вместо обобщения на уровне `Vehicle` и других подобных контрактов

- **DIP (Dependency Inversion Principle)** — был применен принцип инверсии зависимостей (нужно зависеть от удобных абстракций, а не от реализации)

    - `SimpleManager` принимает контракты `Auditor` и `Storage`, благодаря чему ему неважна внутренняя реализация, класс уже запросил только то, что ему нужно

## 2.1. Явно использованные принципы
Наиболее ярко выражено применение `DIP` в `SimpleManager`, а также `SRP` в `Auditor`, `Storage` и `Manager`.

## 2.2 Осознанно ограниченные принципы
Был немного нарушен `ISP` в части полей `brand` и `model` в `Item`, т.к. информация о бренде и модели нужна не всегда. Однако в рамках данной задачи необходимости в разделении нет (выполнение принципа `KISS` (Keep It Simple, Stupid)).

Также в рамках данной задачи сложно говорить о `LSP`, т.к. абстракции относительно "плоские", поэтому моментов, когда принцип следует напрямую применить, не возникает.


# 3. Расширяемость
Полученная система довольно расширяема. Для добавления нового предмета нужно ввести абстракцию в `items.contracts` (или использовать готовые) и добавить реализацию в `items.catalog`. При этом все приложение продолжит работать в штатном режиме. Аналогично можно расширить и `auditors`, `storages`, `managers`.


# 4. Тестирование
Тесты расположены в папке `tests`. Для их написания был использован встроенный модуль `unittest`

# 6. Примечания
## 6.1 Об `uuid`
Поле `uuid` одновременно выполняет роль уникального идентификатора и инвентарного номера предмета на складе.

## 6.2 `ServiceCenter` vs `Auditor`
В оригинальном задании упоминался сервис техосмотра (`ServiceCenter`) для проверки предмета перед приемом на хранение. При решении задания было решено расширить понятие осмотра до понятия аудита.

## 6.3 `typing.Protocol` vs `abc.ABC`
В решении использовано оба возможных подхода описания контрактов в Python: `typing.Protocol` и `abc.ABC`. Область применения подходов была четко разграничена: `abc.ABC` использовался для описания моделей данных (в `items`), а `typing.Protocol` использовался для описания поведения (в `auditor`, `storage`, `manager`)
